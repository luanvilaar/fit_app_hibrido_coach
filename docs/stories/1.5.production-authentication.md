## Story

**As a** atleta FitBlock,
**I want** entrar e criar minha conta com segurança,
**so that** eu possa acessar minha área de treino com uma sessão persistente.

## Acceptance Criteria

1. `/entrar` autentica com e-mail e senha por Supabase Auth.
2. `/criar-conta` cria uma conta e informa quando a confirmação de e-mail for necessária.
3. `/recuperar-senha` solicita recuperação de senha com redirect seguro para a aplicação.
4. A sessão é restaurada ao abrir o app e atualizada via `onAuthStateChange`.
5. Rotas `/app/*` exigem usuário autenticado e redirecionam para `/entrar` quando não há sessão.
6. O atleta consegue sair da conta pela área autenticada.
7. A chave service role nunca é importada ou exposta no bundle web/mobile.
8. O fluxo possui testes para configuração, login/cadastro, logout e proteção de rota sem depender de uma conta real.

## Dev Notes

- O blueprint define e-mail/senha como método inicial, com magic link opcional, Google/Apple em fases posteriores, recuperação e verificação de e-mail. [Source: FITBLOCK-APP-BLUEPRINT.md#28-estratégia-de-autenticação]
- O app precisa manter a área autenticada fora de indexação e separar as rotas públicas `/entrar`, `/criar-conta` e `/recuperar-senha`. [Source: FITBLOCK-APP-BLUEPRINT.md#8.1-área-pública]
- O cliente usa somente a chave pública/anônima; service role fica restrita ao backend/ambiente administrativo. [Source: FITBLOCK-APP-BLUEPRINT.md#17.6-backend]
- O ambiente atual possui variáveis Supabase configuradas, mas o código deve aceitar os nomes públicos `EXPO_PUBLIC_SUPABASE_URL` e `EXPO_PUBLIC_SUPABASE_ANON_KEY` para deploy web/mobile.

### Completion Notes List

- Cliente Expo usa apenas `EXPO_PUBLIC_SUPABASE_URL` e `EXPO_PUBLIC_SUPABASE_ANON_KEY`, com fallback compatível para `SUPABASE_URL` e `SUPABASE_ANON_KEY` locais.
- O `app.config.ts` carrega explicitamente o `.env` da raiz para que `npm run start`, `npm run web` e `npm run build` recebam as variáveis dentro do workspace Expo.
- O web usa referências diretas a `process.env.EXPO_PUBLIC_*`, pois `Constants.expoConfig` não expõe `extra` no runtime web estático.
- O wrapper `with-root-env.cjs` injeta somente as duas variáveis públicas nos comandos Expo; a service role não é repassada por ele.
- A interface de autenticação reutiliza o padrão visual do site: hero `graphite` com acentos `fitblockPurple`, form `canvas` sobre `softCloud` e tipografia editorial; Google não foi adicionado porque permanece fora do escopo do provider inicial.
- `SUPABASE_SERVICE_ROLE_KEY` não é lida pelo app universal nem aparece no bundle web exportado.
- `/entrar`, `/criar-conta` e `/recuperar-senha` estão públicos; `/app/*` exige sessão e oferece logout.
- Campos de e-mail e senha têm ícones, estados acessíveis, foco em mobile e controle de visibilidade da senha.
- Validações executadas: `npm run lint`, `npm run typecheck`, `npm test` — 8 suites, 20 testes — e `npm run build`.
- A validação remota com uma conta real depende de configurar no Supabase as URLs de site/redirect do ambiente publicado.
- O teste de atualização de senha com sessão inválida captura e valida explicitamente a rejeição esperada, evitando uma Promise não tratada no harness.
- Os e-mails de confirmação, boas-vindas e recuperação agora compartilham uma composição compatível com clientes de e-mail, espelhando os tokens grafite, roxo, tipografia e hairlines do sistema Dark Performance.
- O endpoint de boas-vindas marca explicitamente seu propósito, mantendo “Abrir meu treino” quando a conta já nasce confirmada e reservando “Confirmar acesso” para o Auth Hook de cadastro.
- Tipos de Auth ainda sem fluxo dedicado (como troca de e-mail) usam uma mensagem de confirmação própria, no mesmo design system, em vez de alterar por substituição o conteúdo de recuperação de senha.
- Validações desta revisão: `npm run lint`, `npm run typecheck`, `npm test` e `npm run build`.
