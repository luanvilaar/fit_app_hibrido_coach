## Story

**As a** atleta FitBlock,
**I want** abrir o app e encontrar imediatamente o treino de hoje,
**so that** eu saiba o foco da sessão e consiga iniciar meu treino com clareza.

## Acceptance Criteria

1. A aplicação é criada como base universal React Native + Expo + Expo Router + TypeScript, com a estrutura inicial em `apps/universal/` e espaço para pacotes compartilhados conforme o blueprint.
2. A rota inicial apresenta a área autenticada do atleta em modo protótipo, sem depender de backend, usando dados locais explícitos e sem simular autenticação ou pagamentos reais.
3. A tela “Hoje” exibe saudação/status do dia, treino principal, foco, duração estimada, blocos, equipamentos, prontidão simples, resumo semanal, próxima sessão e uma mensagem recente do coach.
4. A ação primária “Iniciar treino” fica visível sem rolagem no desktop e em até três interações no mobile; ao ser acionada, mostra estado de sessão iniciada e feedback visual acessível.
5. O shell desktop utiliza sidebar operacional persistente e o shell mobile utiliza navegação inferior com Hoje, Calendário, Progresso, Loja e Perfil; a seleção ativa é comunicada por texto, ícone e estilo, não apenas por cor.
6. O layout é responsivo nos breakpoints conceituais de 320–639 px, 640–1023 px e 1024 px+, mantendo alvos de toque de no mínimo 44 × 44 px e sem overflow horizontal.
7. A direção visual usa os tokens FitBlock do blueprint: ink `#101114`, canvas `#FFFFFF`, soft-cloud `#F5F5F7`, hairline `#DEDEE5`, texto secundário `#686B82` e roxo de ação `#7132F5`; vermelho fica reservado para erro.
8. A interface usa tipografia display condensada para títulos de destaque e tipografia de interface legível para navegação, métricas e controles, com hierarquia editorial sem copiar a identidade visual dos sites de referência.
9. Controles interativos possuem nome acessível, foco visível no web, estado hover/pressed/disabled quando aplicável, e a implementação respeita `prefers-reduced-motion`/equivalente da plataforma.
10. Os comandos de qualidade definidos no projeto passam para o incremento, ou falhas de ambiente/dependência ficam registradas na story sem mascarar o resultado.

## Dev Notes

### Contexto de produto

- A ação principal do atleta é abrir o app, entender o treino do dia e iniciar a sessão; a loja e o conteúdo devem ficar em posição secundária. [Source: FITBLOCK-APP-BLUEPRINT.md#9.1-tela-hoje]
- O MVP do atleta inclui cadastro/login, home/hoje, calendário, sessão, registro de resultados, prontidão simples, progresso básico, programa/equipe ativa, perfil, notificações in-app e catálogo/compra no web. Esta story cobre apenas o shell prototípico e o primeiro ponto de entrada visual. [Source: FITBLOCK-APP-BLUEPRINT.md#30.1-mvp-do-atleta]

### Direção visual

- O produto combina modo editorial para conteúdo público e modo operacional para dashboard, calendário e execução; esta story deve priorizar o modo operacional. [Source: FITBLOCK-APP-BLUEPRINT.md#14.1-princípio-visual]
- A paleta, escala tipográfica, espaçamento de 8 px, raios e regras de cor abaixo são derivados do blueprint e devem ser tratados como tokens. [Source: FITBLOCK-APP-BLUEPRINT.md#14.2-paleta]
- Sidebar desktop, tabs/bottom navigation mobile, botões com área mínima de 44–48 px e feedback de sistema são componentes previstos no blueprint. [Source: FITBLOCK-APP-BLUEPRINT.md#15-componentes-principais]

### Arquitetura

- O front-end recomendado é React Native + Expo + React Native Web + Expo Router + TypeScript estrito, com componentes compartilhados entre web, iOS e Android. [Source: FITBLOCK-APP-BLUEPRINT.md#17.1-front-end-universal]
- A estrutura inicial deve reconhecer o domínio em `features/` e separar app universal de pacotes compartilhados; nesta primeira story, manter o domínio de treino local e pequeno, sem criar backend prematuramente. [Source: FITBLOCK-APP-BLUEPRINT.md#17.2-estrutura-de-monorepo]
- O blueprint recomenda TanStack Query para dados remotos, Zustand/estado local para UI e persistência offline para sessão em andamento. Não são necessários nesta story enquanto os dados forem fixtures locais. [Source: FITBLOCK-APP-BLUEPRINT.md#17.4-estado-e-dados]

### Restrições

- Não adicionar autenticação real, Supabase, pagamentos, chat, analytics avançado ou marketplace nesta story; esses itens pertencem ao MVP/fases posteriores e dependem das decisões listadas no blueprint. [Source: FITBLOCK-APP-BLUEPRINT.md#35-decisões-que-precisam-ser-aprovadas-antes-da-implementação]
- Não copiar vermelho ou a interface dos projetos de referência; usar roxo FitBlock como ação e a referência apenas para padrões de composição. [Source: FITBLOCK-APP-BLUEPRINT.md#3-referências-analisadas]
- Não alterar `FITBLOCK-APP-BLUEPRINT.md` nem os arquivos da pasta `references/`.

### Project Structure Notes

- O repositório começa sem código de aplicação, sem `package.json` e sem documentação técnica derivada. Os caminhos criados nesta story devem estabelecer a base alinhada ao monorepo recomendado, mantendo o blueprint como fonte do produto.
